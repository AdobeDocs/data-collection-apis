# Troubleshooting

API errors in the Edge Network API can have a variety of causes, internal (Edge Network itself) or external (input, configuration, or upstream related). This page explains how the API reports errors, how to interpret them, and when to retry a request. For a complete list of error codes and the recommended action for each, see [Error codes](error-codes.md).

Error responses include a request ID (`requestId`). Include this value whenever you contact Adobe Customer Care about an error.

## Error categories

| Category | Source | Description | Typical HTTP status |
| --- | --- | --- | --- |
| Request processing | Internal | Unexpected conditions or transient failures within the Edge Network, such as an unexpected error or a temporarily unavailable service. | `500`, `502`, `503`, `504` |
| Input | External | Malformed input and entity validation errors, such as invalid JSON, missing parameters, or invalid identities. | `4xx` |
| Configuration | External | Server-side configuration errors, such as a disabled datastream or a sandbox that cannot be resolved. | `422` |
| Authorization | External | Missing, invalid, or expired access tokens, or insufficient permissions. See [Authentication](authentication.md). | `401` |
| Geographic restriction | External | Requests that originate from a country that is not allowed. | `403` |
| Upstream | External | Communication errors with upstream services, such as Adobe Target or Adobe Journey Optimizer. | `207 Multi-Status` |

## Error severity

Edge Network API errors are also split by severity. Severity determines whether the Edge Network finished processing your request, and how the error is returned.

| Severity | Effect on the request | HTTP status | Where the error appears |
| --- | --- | --- | --- |
| Fatal | Request processing halts, and the request is rejected. | Non-2xx, depending on the error | An `application/problem+json` error object |
| Non-fatal | Request processing continues, but one or more upstream services failed. | `207 Multi-Status` | The `errors` array of the `application/json` response |
| Warning | Request processing continues, but an upstream service reported a condition that might have partially affected the result. | `200` | The `warnings` array of the `application/json` response |

Request processing, input, configuration, authorization, and geographic restriction errors are fatal. Upstream errors are non-fatal.

### Fatal errors

Fatal errors halt request processing and return a non-2xx HTTP status. See [Retry strategy](#retry-strategy) to learn which status codes you can retry.

The response body contains a problem detail, as defined by [RFC 7807 Problem Details for HTTP APIs](https://tools.ietf.org/html/rfc7807). The returned content type is `application/problem+json`. This response contains machine-readable details about the error, including a URI type.

All error objects have `type`, `status`, `title`, `detail`, and `report` properties, so that the API client can tell what the problem is.

| Property | Type | Description |
| --- | --- | --- |
| `type` | String | A URI reference (RFC 3986) that identifies the problem type, in the format `https://ns.adobe.com/aep/errors/<ERROR-CODE>`. See [Error codes](error-codes.md) for the meaning of each error code. |
| `status` | Number | The HTTP status code generated by the server for this occurrence of the problem. |
| `title` | String | A short, human-readable summary of the problem type. |
| `detail` | String | A short, human-readable description of the problem type. |
| `report` | Object | A map of additional properties that aid in debugging, such as the request ID or the org ID. In some cases, it contains data specific to the error, such as a list of validation errors. |

```json
{
   "type":"https://ns.adobe.com/aep/errors/EXEG-0104-422",
   "status":422,
   "title":"Unprocessable entity",
   "detail":"Invalid request (report attached). Please check your input and try again.",
   "report":{
      "errors":[
         "Allowed Adobe version is 1.0 for standard 'Adobe' at index 0",
         "Allowed IAB version is 2.0 for standard 'IAB TCF' at index 1",
         "IAB consent string value must not be empty for standard 'IAB TCF' at index 1"
      ],
      "requestId":"0f8821e5-ed1a-4301-b445-5f336fb50ee8",
      "orgId":"53A16ACB5CC1D3760A495C99@AdobeOrg"
   }
}
```

### Non-fatal errors

Non-fatal errors occur when the Edge Network accepts your request, but one or more upstream services encounter an error while processing it. Unlike fatal errors, non-fatal errors don't halt the request. The response uses the standard `application/json` format, and the HTTP status of the response is `207 Multi-Status`.

Each non-fatal error appears as an object in the `errors` array of the response body, using the same problem detail format as fatal errors. The `status` property of each error object reflects the specific upstream failure, such as `504` for a timeout or `502` for a bad gateway. This value is distinct from the `207` HTTP status of the response, so inspect the response body to understand what happened.

The following example shows a `207 Multi-Status` response for a request where the call to the Adobe Target upstream service failed:

```json
{
  "requestId": "a1b2c3d4-e5f6-7890-abcd-ef1234567890",
  "handle": [],
  "errors": [
    {
      "type": "https://ns.adobe.com/aep/errors/EXEG-0203-502",
      "status": 502,
      "title": "The service call has failed.",
      "detail": "An error occurred while calling the 'com.adobe.target' service for this request. Try again.",
      "report": {
        "eventIndex": 0
      }
    }
  ]
}
```

In non-fatal error objects, the `report` object can include an `eventIndex` property. This property identifies the affected event by its zero-based position in the `events` array of your request.

Non-fatal errors only affect the real-time response capabilities of a request, such as personalization decisions or offers. The following upstream services can fail non-fatally. Error messages refer to these services by their service ID, in place of the `{serviceName}` placeholder.

| Upstream service | Service ID |
| --- | --- |
| Adobe Journey Optimizer | `com.adobe.experience_platform.ajo` |
| Adobe Target | `com.adobe.target` |
| Offer Decisioning | `com.adobe.experience_platform.ode` |
| Edge segmentation | `com.adobe.experience_platform.edge_segmentation` |
| Edge destinations | `com.adobe.experience.platform.edge.destinations` |

Data collection is not affected by non-fatal errors. If the Edge Network accepts your request, your event data is collected for the following services, regardless of any non-fatal errors in the response:

* Adobe Experience Platform, including Real-Time Customer Data Platform and downstream applications
* Adobe Analytics
* Server-side forwarding

<InlineAlert variant="warning" slots="text" />

Do not retry requests that return `207 Multi-Status`. Your event data is collected regardless, and audience realization in Adobe Experience Platform is reconciled for Profile-enabled datasets. Retry only if you need to recover a personalization decision or offer that was not returned. Retried events are ingested again, so you must apply [event deduplication](https://experienceleague.adobe.com/en/docs/experience-platform/collection/use-cases/event-duplication) strategies.

### Warnings

Warnings are mostly informative. They generally represent a potentially transient condition that did not fully impact the request. One example is a partial profile read in the segmentation engine. In this case, the accuracy is impacted to some degree, but the functionality is still delivered.

Warnings appear in the `warnings` array of the response body, using the same problem detail format as errors. A response that contains only warnings returns HTTP status `200`, and each warning has a `status` of `200`. If the response also contains non-fatal errors, the HTTP status of the response is `207 Multi-Status`.

The [`collect`](../endpoints/collect/index.md) endpoint doesn't return warnings. If a `collect` request only produces warnings, the response status doesn't change: the endpoint returns `202 Accepted`, or `204 No Content` when the `silent` parameter is set to `true`.

The following error codes are returned as warnings: [`EXEG-0204-200`](error-codes.md#upstream-service-errors), [`EXEG-0301-200`](error-codes.md#identity-and-consent-errors), and [`EXEG-0303-200`](error-codes.md#identity-and-consent-errors).

```json
{
  "requestId": "72eaa048-207e-4dde-bf16-0cb2b21336d5",
  "handle": [
  ],
  "warnings": [
    {
      "type": "https://ns.adobe.com/aep/errors/EXEG-0204-200",
      "status": 200,
      "title": "A warning occurred while calling the 'com.adobe.audiencemanager' service for this request.",
      "report": {
        "cause": {
          "message": "Cannot read related customer for device id: ...",
          "code": 202
        }
      }
    }
  ]
}
```

## Retry strategy

Base your retry decisions on the HTTP status of the response, not on the `status` property of individual objects in the `errors` array. For example, a `207 Multi-Status` response can contain an error object with a `status` of `504`, but you should not retry that request.

| HTTP status | Meaning | Retriable | Strategy |
| --- | --- | --- | --- |
| `207 Multi-Status` | The request was accepted, but one or more upstream services returned an error. | No | Do not retry. Data collection and audience realization are reconciled regardless. If you specifically need to recover a personalization decision or offer, apply [event deduplication](https://experienceleague.adobe.com/en/docs/experience-platform/collection/use-cases/event-duplication) to avoid duplicate ingestion. |
| `400`, `408`, `413` | The request is malformed, incomplete, or too large. | No | Fix the request. Do not retry without changes. |
| `401 Unauthorized` | The access token is missing, invalid, or expired, or doesn't have the required permissions. | Conditional | Retry only after you refresh an expired access token (`EXEG-0503-401`). Other `401` errors require changes to your credentials or permissions. |
| `403 Forbidden` | The request originates from a country that is not allowed. | No | Do not retry. |
| `422 Unprocessable Entity` | The request failed validation, or the datastream or Experience Platform configuration is invalid. | No | Fix the request or your datastream or Experience Platform configuration. Do not retry without changes. |
| `429 Too Many Requests` | The Edge Network or an upstream service is rate limiting your requests. | Yes | Wait for the duration specified in the `Retry-After` response header before you retry. If you frequently encounter rate limits, see [Performance guardrails](guardrails.md). |
| `500 Internal Server Error` | A generic, catch-all error occurred. | No | Do not retry. Contact Adobe Customer Care and include the `requestId`. |
| `502 Bad Gateway` | The Edge Network received an invalid response from an upstream server, for example because of network issues between servers. | Yes | Retry with [exponential backoff](#exponential-backoff). |
| `503 Service Unavailable` | The service is temporarily unavailable, for example during maintenance. | Yes | Retry with [exponential backoff](#exponential-backoff). If the response includes a `Retry-After` header, wait at least the specified duration before you retry. |
| `504 Gateway Timeout` | The Edge Network request to an upstream server timed out, for example because of network or DNS issues. | Yes | Retry with [exponential backoff](#exponential-backoff). |

### Exponential backoff

When you retry `502`, `503`, or `504` errors, use exponential backoff with the following parameters:

| Parameter | Value |
| --- | --- |
| Initial delay | 1 second |
| Delay increase | Double the delay after each attempt |
| Maximum delay | 60 seconds |
| Maximum retries | 8 |

With these parameters, the delays between attempts are 1, 2, 4, 8, 16, 32, 60, and 60 seconds. If the error persists for more than 10 minutes, contact Adobe Customer Care and include the `requestId`.
